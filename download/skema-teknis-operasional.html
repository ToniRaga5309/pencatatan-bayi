BAB 1
Pendahuluan
Dokumen ini menyajikan draft skema teknis dan catatan operasional dari Sistem Informasi Pencatatan Nama Bayi Baru Lahir yang dikembangkan untuk mendukung operasional Dinas Kependudukan dan Pencatatan Sipil (Disdukcapil) Kabupaten Ngada, Provinsi Nusa Tenggara Timur. Sistem ini dirancang untuk mengoptimalkan proses pencatatan kelahiran yang melibatkan tiga pihak utama, yaitu Puskesmas sebagai penyedia data awal, Disdukcapil sebagai verifikator dan penerbit NIK, serta BPJS Kesehatan sebagai pengakses data NIK bayi untuk keperluan jaminan kesehatan nasional.
Tujuan utama penyusunan dokumen ini adalah memberikan gambaran menyeluruh mengenai arsitektur teknis, skema basis data, spesifikasi antarmuka pemrograman aplikasi (API), mekanisme keamanan, serta catatan operasional yang diperlukan sebagai bahan pertimbangan dalam pengambilan keputusan terkait pengembangan, pemeliharaan, dan pengelolaan sistem secara berkelanjutan. Dokumen ini disusun berdasarkan analisis langsung terhadap kode sumber dan konfigurasi sistem yang telah diimplementasikan.
Sistem dibangun menggunakan arsitektur modern berbasis web dengan teknologi Next.js 16 sebagai framework utama, PostgreSQL (Supabase) sebagai basis data produksi, serta di-deploy pada platform Vercel sebagai infrastruktur serverless. Desain sistem mengadopsi pola soft-delete, role-based access control (RBAC), dan audit logging yang komprehensif untuk menjaga integritas dan akuntabilitas data.

2.3 Pola Desain Sistem
Sistem ini mengadopsi beberapa pola desain (design pattern) yang telah terbukti efektif dalam pengembangan aplikasi web modern. Pertama, pola Serverless Functions digunakan melalui Vercel deployment di mana setiap API route berjalan sebagai fungsi serverless yang independent, memungkinkan scaling otomatis berdasarkan beban permintaan. Kedua, pola Soft Delete diterapkan pada tabel birth_records dengan kolom is_deleted, sehingga data yang dihapus tidak benar-benar hilang dari database namun ditandai sebagai tidak aktif, menjaga traceability data untuk keperluan audit. Ketiga, pola Schema Synchronization yang unik digunakan untuk mengelola evolusi skema database secara runtime tanpa perlu menjalankan migration tradisional, menggunakan direct PostgreSQL connection untuk menambahkan kolom secara idempotent.

4.4 Fitur Import dan Ekspor Excel
Sistem menyediakan kemampuan import data kelahiran dari file Excel (.xlsx/.xls) yang sangat fleksibel. Operator dapat mengunduh template import yang telah disediakan, mengisi data sesuai format, kemudian mengunggah kembali ke sistem. Proses import menggunakan pemetaan kolom yang fleksibel, artinya sistem dapat mengenali berbagai variasi nama kolom seperti "NIK Ibu", "nikIbu", "NIK_IBU", atau "nik_ibu" sebagai kolom yang sama. Validasi dilakukan per baris dengan error reporting yang detail, termasuk deteksi NIK yang tidak valid (bukan 16 digit), format tanggal yang salah, dan nama yang terlalu pendek.
Untuk ekspor, sistem menyediakan enam varian download Excel yang masing-masing memiliki cakupan dan kegunaan berbeda: (1) Ekspor data terverifikasi oleh Admin, (2) Download data baru yang belum pernah didownload, (3) Download register yang sudah pernah didownload, (4) Download seluruh register non-deleted, (5) Download data per Puskesmas oleh Operator, dan (6) Ekspor data dengan NIK bayi oleh BPJS. Seluruh proses ekspor menggunakan library SheetJS (xlsx) untuk menghasilkan file XLSX yang kompatibel dengan Microsoft Excel dan Google Sheets.
BAB 5
Keamanan dan Autentikasi
5.1 Mekanisme Autentikasi
Sistem menggunakan NextAuth.js v4 dengan Credentials Provider untuk autentikasi berbasis username dan password. Mekanisme ini menghasilkan token JWT (JSON Web Token) yang disimpan sebagai cookie HTTP-only pada browser klien. Durasi sesi diatur selama 15 menit dengan mekanisme refresh otomatis setiap 5 menit melalui konfigurasi TanStack Query refetchInterval. Sebelum sesi kedaluwarsa, sistem menampilkan peringatan 2 menit sebelum timeout, memberikan kesempatan kepada pengguna untuk memperpanjang sesi tanpa kehilangan data yang belum disimpan.

5.2 Otorisasi Berbasis Peran (RBAC)
Sistem mengimplementasikan Role-Based Access Control (RBAC) ketat dengan tiga peran yang masing-masing memiliki akses terbatas sesuai fungsinya. Otorisasi diterapkan pada dua lapisan: lapisan middleware untuk proteksi rute halaman, dan lapisan API route untuk proteksi endpoint data. Middleware hanya memeriksa keberadaan cookie sesi, sedangkan validasi peran yang sesungguhnya dilakukan pada setiap endpoint API melalui fungsi getCurrentUser() yang memanggil getServerSession() dan memverifikasi role pengguna.

5.3 Proteksi Rute (Middleware)
Middleware Next.js diimplementasikan pada file src/middleware.ts yang berfungsi sebagai gatekeeper pertama sebelum pengguna mengakses halaman yang dilindungi. Middleware ini mencocokkan pola rute /admin/:path*, /operator/:path*, /bpjs/:path*, /profile/:path*, dan /dashboard/:path*. Jika cookie sesi (next-auth.session-token atau __Secure-next-auth.session-token) tidak ditemukan, pengguna akan diarahkan ke halaman login dengan menyimpan URL asli sebagai callback URL untuk redirect setelah login berhasil. Perlu dicatat bahwa middleware hanya memeriksa keberadaan cookie, bukan validitas token atau peran pengguna. Validasi penuh dilakukan pada level API route.
5.4 Validasi Input Data
Seluruh input data dari pengguna divalidasi menggunakan library Zod sebelum diproses lebih lanjut. Validasi ini mencakup panjang karakter minimum dan maksimum, format NIK (tepat 16 digit angka), format tanggal kelahiran, jenis kelamin yang valid, serta pembersihan nama (trim dan konversi ke UPPERCASE). Validasi berlaku pada semua endpoint yang menerima data dari pengguna, baik melalui form submission maupun file upload, sehingga mencegah serangan injection dan memastikan konsistensi data di dalam database.
5.5 Audit Logging
Sistem mencatat seluruh aktivitas kritis ke dalam tabel audit_logs dengan informasi yang mencakup: pengguna yang bertindak, jenis aksi, entitas yang terpengaruh, alamat IP klien, dan user agent browser. Sembilan jenis aksi dicatat: LOGIN, LOGOUT, CREATE, UPDATE, DELETE, VERIFY, REJECT, EXPORT, dan VIEW. Pencatatan log menggunakan pola fire-and-forget (.catch(() => {})) yang berarti proses logging tidak menghambat atau memperlambat respons API terhadap pengguna. Admin dapat melihat seluruh log audit dengan fitur filter berdasarkan jenis aksi, entitas, dan rentang tanggal, serta memiliki kemampuan untuk menghapus seluruh log audit (setelah sebelumnya menyimpan satu entri CLEAR_AUDIT_LOGS sebagai catatan).
BAB 6
Catatan Operasional
6.1 Manajemen Sesi dan Timeout
Sistem menerapkan kebijakan sesi ketat dengan durasi 15 menit untuk menjaga keamanan data, terutama mengingat sifat sensitif data kependudukan yang ditangani. Ketika sesi hampir kedaluwarsa, sistem menampilkan peringatan berupa toast notification 2 menit sebelum timeout dan modal dialog saat sesi benar-benar berakhir. Pengguna diberikan opsi "Perpanjang Sesi" yang memanggil session update melalui API. Pendekatan ini menyeimbangkan antara keamanan (sesi pendek) dan pengalaman pengguna (peringatan dini dan opsi perpanjangan). Konfigurasi refetchInterval 5 menit pada TanStack Query SessionProvider memastikan sesi tetap aktif selama pengguna berinteraksi dengan sistem.
6.2 Schema Synchronization Engine
Sistem menggunakan mekanisme unik yang disebut Schema Synchronization Engine untuk mengelola evolusi skema database tanpa menggunakan Prisma migration tradisional. Komponen ini diimplementasikan dalam file src/lib/schema-sync.ts dan bekerja dengan koneksi PostgreSQL langsung (bukan melalui Prisma Client) untuk menjamin keandalan bahkan ketika Prisma client mengalami masalah. Mesin ini beroperasi dengan dua mekanisme penting: pertama, time-based cache selama 10 menit yang mencegah sinkronisasi berulang dalam waktu singkat, dan kedua, deduplication yang memastikan hanya satu proses sinkronisasi yang berjalan pada satu waktu meskipun ada panggilan bersamaan.
Proses sinkronisasi melakukan langkah-langkah berikut secara berurutan: (1) menambahkan kolom yang belum ada menggunakan ALTER TABLE ADD COLUMN IF NOT EXISTS, (2) memastikan kolom nullable benar menggunakan DROP NOT NULL, (3) memperbaiki nilai NULL pada kolom is_deleted, (4) memastikan keberadaan tabel audit_logs, birth_record_files, dan pengaduan beserta constraint dan indeksnya, serta (5) menambahkan foreign key yang mungkin belum ada. Pendekatan idempotent ini memungkinkan sinkronisasi dijalankan berkali-kali tanpa menyebabkan error, sehingga aman dipanggil pada setiap request API.
6.3 Penyimpanan Berkas
Berkas pendukung kelahiran (Surat Keterangan Lahir dan Kartu Keluarga) disimpan dalam format base64-encoded string langsung di kolom file_data pada tabel birth_record_files. Pendekatan ini memiliki kelebihan berupa kesederhanaan arsitektur, tidak memerlukan konfigurasi layanan penyimpanan eksternal, dan memastikan konsistensi antara data dan berkas dalam satu transaksi database. Namun, pendekatan ini memiliki konsekuensi terhadap ukuran database yang lebih besar dibandingkan penyimpanan berkas di layanan object storage terpisah. Setiap berkas dibatasi maksimal 5MB dengan tipe yang diizinkan hanya image/* (JPG, PNG, dll.) dan application/pdf.
Kebijakan Unggah Berkas
Tipe diizinkan: image/* dan application/pdf. Ukuran maksimal: 5MB per berkas. Jumlah per record: 1 SKL + 1 KK (mengganti jika sudah ada). Kebijakan replace: setiap tipe berkas hanya boleh satu, unggahan baru menggantikan yang lama.
6.4 Manajemen Data dan Soft Delete
Sistem menerapkan pola soft-delete pada data kelahiran melalui kolom is_deleted. Ketika Operator menghapus data kelahiran, record tidak benar-benar dihapus dari database melainkan ditandai sebagai is_deleted = true. Pendekatan ini menjaga traceability data untuk keperluan audit dan investigasi. Data yang telah ditandai sebagai dihapus tidak ditampilkan pada daftar aktif namun tetap ada di database. Beberapa batasan diterapkan pada aksi hapus dan edit: data yang sudah didownload oleh Admin tidak dapat diedit atau dihapus oleh Operator, melainkan harus melalui koordinasi langsung dengan Admin Dukcapil.
6.5 Fitur Dark/Light Mode
Sistem mendukung tema gelap (dark mode) dan terang (light mode) yang diimplementasikan menggunakan library next-themes v0.4.6. Strategi yang digunakan adalah class-based (menambah/menghapus class "dark" pada elemen HTML), dengan tema default adalah "light". Sistem juga mengaktifkan deteksi preferensi OS melalui konfigurasi enableSystem, sehingga pengguna yang mengatur sistem operasinya dalam mode gelap akan otomatis melihat aplikasi dalam tema gelap saat pertama kali mengakses. Toggle tema tersedia pada navigasi bar setiap dashboard (Admin, Operator, BPJS) dan halaman profil. Transisi antar tema menggunakan animasi CSS rotation dan scale pada ikon matahari/bulan untuk pengalaman visual yang halus.
BAB 7
Infrastruktur dan Deployment
7.1 Lingkungan Hosting
Sistem di-deploy pada infrastruktur Vercel sebagai platform serverless yang menyediakan auto-scaling, CDN global, dan SSL certificate otomatis. URL produksi sistem adalah https://pencatatan-bayi.vercel.app. Proses deployment dilakukan melalui Vercel CLI dengan perintah vercel --prod yang melakukan build (prisma generate + next build), upload artefak, dan deploy ke edge network Vercel secara otomatis. Tidak terdapat file vercel.json khusus, sehingga sistem menggunakan konfigurasi default Vercel yang sudah dioptimalkan untuk aplikasi Next.js.
7.2 Konfigurasi Database
Basis data PostgreSQL di-hosting pada layanan Supabase Cloud dengan dua jenis koneksi yang dikonfigurasi melalui environment variable. DATABASE_URL menggunakan Supabase Session Pooler (port 6543) yang dioptimalkan untuk koneksi serverless, sedangkan DIRECT_DATABASE_URL menggunakan koneksi langsung untuk keperluan migration saja. Prisma Client dikonfigurasi menggunakan adapter-pg untuk kompatibilitas penuh dengan environment serverless Vercel, mengatasi keterbatasan koneksi tradisional yang tidak mendukung environment serverless.

7.5 Akun Default Sistem
Sistem menyediakan mekanisme seeding untuk menginisialisasi data awal termasuk akun pengguna dan data Puskesmas. Terdapat satu akun Admin utama, satu akun BPJS, dan 25 akun Operator (satu per Puskesmas). Password default menggunakan pola {nama_puskesmas_lowercase}123 untuk Operator, admin123 untuk Admin di lingkungan seeding, dengan password produksi yang lebih kuat untuk lingkungan live.
Catatan Keamanan
Password default HANYA untuk lingkungan seeding/development. Pada lingkungan produksi, password Admin menggunakan kombinasi yang lebih kuat. Disarankan untuk segera mengubah password default setelah deployment pertama.

8.2 Komponen Kustom Utama
Di samping komponen shadcn/ui yang digunakan secara luas, sistem memiliki beberapa komponen kustom yang dikembangkan khusus untuk kebutuhan aplikasi. Komponen SessionProvider membungkus NextAuth dengan konfigurasi refetchInterval dan refetchOnWindowFocus untuk menjaga sesi tetap segar. Komponen SessionTimeoutWarning menangani logika peringatan timeout sesi yang mendekati masa berlaku. Komponen ThemeToggle menyediakan toggle tema gelap/terang dengan animasi CSS, sementara SortableHeader menyediakan header tabel yang dapat diurutkan dengan indikator arah sorting. Selain itu, terdapat custom hooks seperti useTableSort untuk sorting tabel dengan persistensi URL, useMobile untuk deteksi viewport mobile, dan useClientSort sebagai alternatif sorting di sisi klien.
BAB 9
Ringkasan dan Rekomendasi
9.1 Ringkasan Teknis
Sistem Informasi Pencatatan Nama Bayi Baru Lahir yang dibangun untuk Disdukcapil Kabupaten Ngada merupakan aplikasi web modern dengan arsitektur three-tier yang menghubungkan tiga pihak utama dalam proses pencatatan kelahiran. Sistem menggunakan 6 tabel database relasional, lebih dari 55 API endpoint, dan 17 halaman antarmuka yang mencakup fungsi input data, verifikasi, penerbitan NIK, audit logging, pengaduan, analitik, dan ekspor-impor data Excel. Keamanan dijaga melalui autentikasi JWT, RBAC ketat, validasi input Zod, dan audit trail yang komprehensif.
9.2 Catatan untuk Pengembangan Selanjutnya
Beberapa aspek yang perlu diperhatikan untuk pengembangan dan pemeliharaan ke depan meliputi pertimbangan migrasi penyimpanan berkas dari base64 di database ke object storage (seperti Supabase Storage) untuk efisiensi ukuran database, implementasi rate limiting pada endpoint API untuk pencegahan brute force, penambahan notifikasi email atau WhatsApp untuk pemberitahuan status verifikasi kepada Operator Puskesmas, serta pengembangan fitur pencarian lanjutan dan pelaporan yang lebih komprehensif untuk mendukung pengambilan keputusan berbasis data di tingkat manajerial.
